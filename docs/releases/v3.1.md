# v3.1 "Long Reads": a second sequencing technology, a cohort view, and a site you can find your way around

3.1 makes the pipeline handle **long reads** (PacBio HiFi and Oxford Nanopore) next to short reads, locally and in the cloud,
and benchmarks HiFi on a GIAB truth set. It adds a **cohort view** in Hail and PySpark, a **GitLab mirror** with its own CI,
and gives the web UI a redesign with **site navigation**.

**Every number below was measured on this pipeline** and names its source: a pull request or a run name.
**Draft**: not tagged yet. Tagging and the GitHub Release are the maintainer's call.

## Highlights

**Long reads** ([#288](../../../../pull/288) app, [#294](../../../../pull/294) cloud, [docs/long-read.md](../long-read.md))
- **One table, `READ_TYPES` in `app/tasks.py`, decides everything per read type:**

  | `READ_TYPE` | Aligner | Duplicates | bcftools mpileup | DeepVariant model |
  | :--- | :--- | :--- | :--- | :--- |
  | `short` (default) | bwa-mem2 (unchanged) | marked | defaults | WGS |
  | `hifi` | `minimap2 -ax map-hifi` | not marked | `-X pacbio-ccs` | PACBIO |
  | `ont` (R10.4.1 Q20+) | `minimap2 -ax lr:hq` | not marked | `-X ont` | ONT_R104 |

- **minimap2 2.28** in the image, as a sha256-pinned upstream binary. Its version, the preset and whether duplicates
  were marked go into the run record.
- **Refused before any download:** a short-read aligner with long reads, paired long reads, a DeepVariant model that
  disagrees with the read type, and pangenome-aware DeepVariant on long reads.
- **In the cloud** ([#294](../../../../pull/294)): an optional `read_type` execution input (`short` | `hifi` | `ont`).
  - `Check_Read_Type` sends long reads to minimap2 and gives every calling job the read type. That covers DeepVariant
    and its fallback to bcftools, the split-mode parts and the bcftools shards and merge.
  - Anything else fails with `UnknownReadType`, and a short-read aligner with long reads fails with
    `AlignerNotForLongReads`. Both happen before any job, and they close the run record and notify.
  - Short-read runs keep their routes and jobs. 271 Step Functions Local tests pass, 21 of them new long-read cases.
- **Not yet:** an upload can't say it is long reads; the trigger starts every upload as short reads (#295). Long-read
  runs are started by hand until then.

**Long reads, measured**
- **Benchmark: PacBio HiFi HG002 chr20** ([#293](../../../../pull/293), local, offline). minimap2 `map-hifi` and DeepVariant
  1.10.0 `--model_type=PACBIO` on the GPU, scored with hap.py against GIAB v4.2.1:

  | Type | TP | FN | FP | F1 |
  | :--- | ---: | ---: | ---: | ---: |
  | SNP | 71,282 | 51 | 16 | **0.999530** |
  | Indel | 11,174 | 82 | 90 | **0.992499** |

  - This reproduces Google's DeepVariant 1.10 PacBio case study (HG003 Revio 32x chr20: SNP 0.999067, indel 0.993679).
  - Outside GIAB's difficult regions: 5 errors in 63,782 truth variants.
  - Caveat: v4.2.1 for HG002 integrates HiFi evidence.
- **Cloud checkpoint: CLOUDLR001** ([#300](../../../../pull/300), 12 Nov 2026). 4,199 HG002 HiFi reads over
  chr20:10-12 Mb, started with `read_type: hifi` and `caller: deepvariant`.
  - **Every stage succeeded on its first Batch attempt:** minimap2 align in 33 s (4 vCPU / 8 GB, peak 660 MiB), then
    DeepVariant PACBIO in 1.3 min on a g6.4xlarge after 4.5 min of instance boot.
  - **Wall time 8.8 min,** about $0.006 of Fargate plus the GPU instance.
  - **Identical to the local 30x DeepVariant in that window:** SNP F1 1.000000, indel F1 0.997700, the same 3,367
    PASS records.
  - **The execution ends FAILED at the quality gate, by design:** 2 Mb of chr20 is far too shallow for a
    chromosome (mean depth 0.925 against a minimum of 20). Every other check passed.

**Cohort QC with Hail and PySpark** ([#292](../../../../pull/292), [docs/cohort-qc.md](../cohort-qc.md))
- **`scripts/cohort_qc.py`** (Hail 0.2.139 on Spark 3.5) reads every sample's bcftools, DeepVariant and pangenome
  DeepVariant VCFs into one MatrixTable. It compares the callers per sample by sites, as bcftools stats and the
  quality gate count them.
  - HG003, PASS calls: bcftools 133,624 (Ti/Tv 1.843), DeepVariant 107,189 (2.067), pangenome DeepVariant 108,291
    (2.010).
  - 99,979 sites are called by all three, and 29,167 only by bcftools. The run takes 2.0 min.
- **`scripts/cohort_runs.py`** (plain PySpark 3.5.4, the AWS Glue 5.0 version) flattens `runs/*.provenance.json` into
  one row per sample: stage times, CPU, peak memory and gate stats. A Glue entry point is included.
- **A CI job, "Cohort QC (Hail, PySpark)",** runs on Java 11 when cohort files change and always on main.

**Reproducible alignments** ([#283](../../../../pull/283))
- bwa and bwa-mem2 now use a fixed batch size (`-K 100000000`) in both align routes. The old default batch scaled
  with the thread count, so the same reads could align slightly differently on 4 vCPUs and on 16 threads.
- Synthetic data aligns byte-identically to before.
- Real samples bigger than one batch change slightly. Numbers recorded before this change stay as recorded.

**The web UI: redesign and navigation**
- **A light, Google-style redesign** ([#269](../../../../pull/269)):
  - four themes: light, dark, retro and high contrast;
  - the Geyser logo;
  - helix stage status;
  - Turbo-coloured figures with a 2D/3D toggle.
- **Follow-ups:**
  - one progress helix across the stages, base chips in every light theme, and DeepVariant/AlphaGenome shortcuts on
    the sample list ([#276](../../../../pull/276));
  - decorative motion motifs for DeepVariant and AlphaGenome ([#274](../../../../pull/274));
  - 2D figures in linear Turbo over each figure's median ± 2·IQR ([#275](../../../../pull/275));
  - the logo erupts on first interaction, at about 0 bytes of HTML ([#281](../../../../pull/281)).
- **Site navigation** ([#285](../../../../pull/285)):
  - **Header:** Samples · Results (3D) · Upload · How it works · GitHub, a Menu button on narrow screens and a compact
    Theme menu.
  - **Each sample page:** a breadcrumb, a sticky "On this page" bar and previous/next links.
  - **Footer and new page:** a footer with the links, and a new **How it works** page.
- **The header helix shows on half-screen windows again** ([#302](../../../../pull/302)). It shrinks to fit and hides
  only at 1000 px or less; since #285 it had disappeared below 1320 px.
- **The hosted upload page** uses the local UI's two-card layout ([#290](../../../../pull/290)). Uploads go up to
  256 GiB per file on both the local UI ([#272](../../../../pull/272)) and the hosted site
  ([#271](../../../../pull/271)).
- **Speed budgets, kept honest** ([#279](../../../../pull/279), [#285](../../../../pull/285)):
  - Lighthouse now judges each metric on its own median over 5 runs; one run's spike used to decide.
  - The live Django UI gets LCP < 1.1 s. The published site that visitors get keeps < 1 s, 30 KB per page and TBT
    < 50 ms. On #285's final runs the published sample page loaded in 903 ms and the figures page weighed 29.9 KB.

**CI and delivery**
- **Docs-only pull requests skip the heavy jobs** ([#286](../../../../pull/286)): about 2 min instead of about 8. A
  broken change detector runs the full suite.
- **A one-way GitLab mirror** of `main` and the `v*` tags, plus a GitLab CI pipeline (ruff and the unit tests)
  ([#297](../../../../pull/297), [#298](../../../../pull/298), [#299](../../../../pull/299)). GitHub stays the source of
  truth, and the push only fast-forwards.
- **The large route's S3 behaviour, tested offline** with moto's S3 server ([#278](../../../../pull/278), closes #231):
  presigned GETs, range reads, and a VCF equal to the single-job route's.
