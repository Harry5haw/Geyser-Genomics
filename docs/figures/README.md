# Signature figures

Generated by `scripts/figures/<name>.py`, never drawn by hand. Each script turns its source into a small
derived CSV in `csv/` (per-window or per-bin summaries: no reads, positions or genotypes), then draws
from that CSV to PNG (200 dpi) + SVG. Re-running on the same CSV gives byte-identical files (tested in
`tests/test_figures.py`). One palette and style for all of them: `scripts/figures/figkit.py` (the
`dataviz` skill's validated reference palette: categorical slots in fixed order, sequential blue for
magnitude, ink-coloured text, hairline grids).

Needs `pip install -r requirements-figures.txt` (matplotlib; included in `requirements-dev.txt`).

## Regenerating

From the repo root, with geyser-data next to the repo (`G=../geyser-data`):

```bash
# 2. Coverage terrain: windowed depth first (geyser-app image has mosdepth + samtools), then the CSV and figure
mosdepth -n --fast-mode --by 500000 HG003_chr20 HG003_chr20.bam        # per BAM, in Docker
python scripts/figures/coverage_terrain.py --from-mosdepth "HG003 35x (bwa)=HG003_chr20.regions.bed.gz" ... \
    --csv docs/figures/csv/coverage-terrain.csv --out docs/figures/coverage-terrain

# 3. Per-base quality
Q=$G/real-inputs/results/bucket/qc_reports
python scripts/figures/quality_surface.py --from-fastp "HG003 35x=$Q/REAL-HG003-35x-chr20.fastp.json" ... \
    --csv docs/figures/csv/quality-surface.csv --out docs/figures/quality-surface

# 4. Variant density ("SAMPLE|caller" labels group the rows)
python scripts/figures/variant_density.py --from-vcf "HG003|bcftools=$G/variants/HG003_chr20.vcf.gz" ... \
    --csv docs/figures/csv/variant-density.csv --out docs/figures/variant-density

# 5. DeepVariant batch x shards (local GPU; one container at a time, ~2.3 h for the 13 runs)
python scripts/benchmark_dv_grid.py --root $G/dv-grid/bucket --sample HG003_chr20 --reference GRCh38_chr20.fa \n    --batch-sizes 128,256,512,1024 --shards 16,8,4 --repeat 256x16 --dv-image geyser-deepvariant --dv-memory 12g \n    --out $G/dv-grid/results
cp $G/dv-grid/results/dv-grid.csv docs/figures/csv/dv-batch-shards.runs.csv
python scripts/figures/dv_batch_shards.py --from-grid docs/figures/csv/dv-batch-shards.runs.csv \n    --csv docs/figures/csv/dv-batch-shards.csv --out docs/figures/dv-batch-shards \n    --title "DeepVariant on HG003 chr20 (RTX 3080): batch size x make_examples shards"

# Redraw any figure from its committed CSV alone
python scripts/figures/variant_density.py --csv docs/figures/csv/variant-density.csv --out docs/figures/variant-density
```

The exact label lists used are in the commit that added each CSV (and in the PR).

## Reading them

- **Coverage terrain.** One ridge per BAM, same depth scale for all; depth is clipped at 2.5 x the
  overall median (marked `|`). Flat at the median along the arms; around the centromere (26-31 Mb, which
  GRCh38 fills with modelled satellite sequence) depth rises to ~1.7x the median (HG003 35x: 60-65x
  against 38x), and one 500 kb window at 31.0-31.5 Mb is a spike in every BAM (Google's four BAMs 119-126x,
  Geyser's bwa 87x, giraffe 79x): most likely reads from repeat copies piling up on the reference's one
  copy, the same region where bcftools makes its excess calls in the variant-density figure. Along the
  arms Google's and Geyser's alignments of the same HG003 35x reads match (mean difference 0.7x); they
  differ mainly in those pericentromeric windows. vg giraffe's ridge is lower there (26.5-30 Mb: 49x vs
  57x for Geyser's bwa). Geyser's bwa and bwa-mem2 ridges are identical (same depth in all 129 windows,
  same base count): bwa-mem2 reproduces bwa mem's alignments by design, as the aligner benchmark already
  showed (same duplicates, no calls unique to either). Google's vg giraffe BAM of the same reads sits
  higher everywhere (median 43x vs 38x); why was not checked (duplicate flagging is one candidate).
- **Per-base quality.** Mean Phred per cycle; quality falls towards the 3' end and R2 is lower than
  R1, as expected for Illumina (HG003 35x: R1 35.9 at cycle 1 to 34.3 at cycle 151, R2 35.6 to 33.5).
  The HG003 rows are near-identical because the 15x/30x inputs were downsampled from the same reads, and
  the HG003 single-end run's quality equals the paired run's R1. The HG005 single-end row is not the
  paired run's R1 (slightly lower throughout), so that input was built differently.
- **Variant density.** A record counts if its FILTER is PASS or "." (none set). The pipeline's
  `bcftools call -mv` sets no FILTER, so the bcftools rows are *every* call (the VCF as written; hap.py's
  `--pass-only` also keeps "." records, so this is what the benchmark scored), while the DeepVariant rows are its PASS calls. Read the gap as "raw bcftools vs
  filtered DeepVariant", not as a like-for-like filtered comparison. Next to the centromere (28-31 Mb)
  bcftools makes about 4x as many calls per Mb as either DeepVariant (HG003, 29-30 Mb: 16,421 vs 3,763
  and 3,623), most likely from reads mismapped in the pericentromeric repeats; over all of chr20 it makes
  ~25% more (132k vs 105k for HG003). Linear and pangenome DeepVariant are almost indistinguishable at this scale. The colour scale stops at
  the 98th percentile so the rest of the chromosome stays readable; the note on the figure says how
  many bins are above it.
- **DeepVariant batch x shards.** Three panels on one grid: the whole stage, `call_variants` alone, and how
  busy the GPU was during `call_variants`.
  - **Shards set the time.** Going from 16 to 8 to 4 `make_examples` shards takes the stage from about
    8 min to 9-10 to 13.5-16 (`make_examples` 324-350 s, 396-460 s, 657-779 s). The machine has 16 hardware
    threads, so 16 shards is the most this measures.
  - **Batch size hardly matters, up to 512.** `call_variants` takes 100-108 s at batch 128, 256 and 512, and
    124-131 s at 1024 (Google's default) in every row, about 20% slower. The 10 GB card runs linear
    DeepVariant at 1024: only pangenome-aware DeepVariant ran out of memory there.
  - **The GPU stays mostly idle:** 26-33% busy during `call_variants` in every cell, with 9.5-9.8 GB
    reserved (TensorFlow takes nearly all free VRAM whatever the batch).
  - **Noise.** The repeat of 256 x 16 took 474 and 485 s. In the 4-shard row `make_examples` drifts upwards
    from left to right (657 to 779 s), although batch size can't affect it. The host was shared with other
    work during the grid, so read that spread as noise of about ±9%, not as an effect of batch size.
  - **Calls.** Every run sent the same 79,759 examples to `call_variants`, but no two runs wrote byte-identical
    records, not even the repeat. PASS counts vary by at most 2 of 105,403 (85,652-85,653 SNPs,
    19,883-19,884 indels). GPU inference isn't bit-reproducible run to run, and the settings themselves
    don't change the calls.
